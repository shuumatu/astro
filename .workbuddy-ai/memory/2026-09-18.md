# 2026-09-18

## 日食与月食演示：用户复核后的一轮修正

用户指出四处问题，逐一核实后确认其中两处是真 bug。

**1. 地球自转轴方向反了（真 bug，且在共享模块里）**
`engine/earthGlobe.ts` 用 `axialTilt.rotation.x = +obliquity`，在黄道坐标系里把地轴放到了 `(0, −sinε, cosε)`；正确值是 `(0, +sinε, cosε)`（倾斜指向黄经 90°，即六月至点）。用 `Astronomy.Ecliptic(EQJ 北极)` 实测确认。倾角大小一样，只是朝了另一个至点——**季节是反的，而原来的测试只断言角度，所以一直没发现**。已改为负号，并把测试改成断言**方向**。

**2. 月球完全没有轴倾角（真 bug）**
月球用的是裸 `SphereGeometry`，贴图的北极落在球体局部 +Y，而场景的北是 +Z，所以月球是「躺着」的。改为用真实天体坐标系定向。

**3. 黄道面等标签位置不对（真 bug）**
两个原因叠加：
- 标签锚点沿黄道 +Y 偏移，但内容是在黄道坐标系里写的、到图最顶层才转成 y-up，所以 +Y 指向**相机**而不是屏幕上方 → 标签落在天体正中。改成沿 +Z。
- 平面标签固定在黄经 0°，而相机是垂直于日—月连线摆放的，所以日期一变标签就从盘面边缘荡到画面中间、甚至压在地球上。改成每帧取相机 right 向量投影到黄道面。

**4. 天体比例**
太阳视觉半径 1.0→1.5（日地比 1.11→1.70），月轨 3.6→4.6（月轨/地球半径 4.0→5.2），日地距离 7→8.5。太阳的绘制大小纯属视觉——影锥全部由真实半径与距离算出后再缩放，改它不影响任何物理。

**其它修正**
- 标签避让从「半径阈值」改成「矩形盒测试」：两个标签同 x 但纵向拉开本就不重叠，半径阈值会白白丢掉一个。
- 影锥三个标签按三角形排布（本影在轴上，半影与伪本影同侧、分列两端），否则半影标签总是被挤掉——而「本影与半影靠标签区分」正是需求。
- 读数与面板会短暂不一致：读数节流 0.5 s，而环食阶段在播放速度下只有约 1 秒，会整个被跳过。改为 kind 变化时立即发布。
- 播放速度改成随事件长度自适应（整场约 45 秒），并通过 `onSettingsResolved` 回报给外壳。
- 拖动时间轴即暂停（否则时钟与拖动打架）；`prefers-reduced-motion` 下不自动播放。
- 局部日食搜索加了守卫：观测点远离食带时 `SearchLocalSolarEclipse` 会返回**另一场**食，直接采用会把时间轴整体挪走。

**新增交互**：跳到食甚、回到中心食带、移到偏食带（在候选偏移里搜索第一个偏食位置）、相位色带图例。

**验证**：vue-tsc 干净；vitest 39 文件 339 用例全过（新增 11 例，含地球极轴方向、月球近地面朝地、地球子午线随恒星日旋转）；无头 Chrome 截图核对四个状态；vite build 成功。

**教训**：欧拉角的正负号本身不自证。凡是「朝向」类的量，用两个方向向量（极点 + 本初子午线）表达并断言方向，而不是断言角度——角度对了方向仍可能反。

## 补：把新增交互真正跑了一遍

上一轮加的交互只写了没验，这轮补验，并因此发现一个真问题。

**「读数是陈旧的」这一类 bug 的根因**：命令处理函数（`scrubTo` / `setObserverOffset` / `selectEvent`）改完 `timeMs` 就立刻 `publishState()`，但 `kind` 要等下一帧 `apply*Geometry()` 才更新——于是面板会短暂（无头环境下是整段）显示上一时刻的食相，而且面板与左下角读数会互相矛盾。修法是把「读数字」和「摆三维」拆成两步：`readSolarReadouts()` / `readLunarReadouts()` 只算标量，`placeSolarCones()` / `placeLunarCones()` 只摆网格；命令处理函数在发布前先 `refreshReadouts()`。顺带好处是影锥不会用上一帧的月球位置去摆。

**验证方式**：临时加一个 `?cmd=<json>` 参数把命令直接送进 `runCommand()`，用 `--dump-dom` 读面板状态。确认：
- `scrub-to-peak` → 跳到食甚（环食）并暂停；
- `observer-preset off-path` → 在中心食带上是**环食**，偏 2° 后变**偏食**（与单测里「偏移 < 8°」一致）；
- `toggle shadows` → 三个影锥标签消失，`peak` 标签补位；
- 面板与读数不再矛盾。

**把搜索抽成纯函数**：`findPartialOffset(kindAt, step, limit)` 放进 `geometry.ts`，场景只提供回调。这样搜索逻辑可单测（含环形推进顺序、到限即停、限内无解返回 null），并加了一条真实事件的集成测试：2027-08-02 日全食，从中心食带出发必须能在 8° 内走到偏食。

**注意**：单测里 `findPartialOffset` 的调用顺序断言暴露了我对「环」的预期写错了——它是先问完一圈四个方向再外扩，不是沿一条线推进。测试写错时先怀疑测试。

## 补二：观察者视角与移动端

**观察者视角**：桌面端渲染出一枚标准的日环食金环（月球正好落在日面中央、留一圈亮环），这是几何正确的直接回报。移动端加了「窄屏默认折叠面板」——之前展开的面板几乎盖满屏幕，把切换过去要看的圆面挡住了。

**发现一个 app 级问题（不是本演示引入的）** —— **这条结论是错的，见下。**

**更正：并不存在横向溢出。** 我一度断言「390×844 下 canvas 是 526，页面横向溢出 136px，所有演示页都这样」，并建议改全局页头。**这是错的。** 往 `<title>` 里临时写诊断值后发现：`doc.clientWidth = 526`、`scrollWidth = 526` —— 两者相等，说明**根本没有溢出**，是布局视口本身就是 526。逐档测 `--window-size`：请求 400/500 都被夹到 526，560→534，620→594，800→774（差额 26 是滚动条），`scrollWidth` 始终等于 `clientWidth`。**是 headless Chrome 在 Windows 上的最小窗口宽度把 390 夹成了 526**，而 `--screenshot` 仍按 390 裁图，于是画面右侧被裁掉——看起来像溢出，其实没有。

**正确做法**：用 iframe 固定 390px 宽来量真实窄屏布局。实测 390×760：页头正常换行、日—地—月与影锥完整可见、标签按盒测试适度稀疏、面板折叠成一条标题栏 ✓。**移动端布局本来就是好的。**

**教训（重要）**：`--window-size` 在小宽度上不可信，别用它验证移动端；要么用 iframe 定宽，要么用 CDP 的 `Emulation.setDeviceMetricsOverride`。更一般地：**先量、且量对**——我这次「先量」了 canvas 宽度却误读了它，还据此向用户报了一个不存在的 bug。诊断值要打到能读到的地方（`<title>` 就很方便），并且必须包含 `scrollWidth` vs `clientWidth` 这对判据。

保留的改动仍然成立：窄屏默认折叠面板（真实 390px 下面板 280px 宽，展开会盖住大半个舞台）；`cameraFramingFill` 的 aspect 下限 0.6 → 0.35（`body` 有 `min-width: 320px`，320/640 = 0.5 时旧下限会横向切）。

## 补三：标签悬停说明 + 平面标签位置

**平面标签位置**（用户要求）：两个平面标签改到**同一侧**，月球轨道面在上、黄道面在下。做法是取相机 right 投影到黄道面的方向 `direction`，再投影到月球轨道面得 `inPlane`；若 `inPlane.z < 0` 就**同时取反两者**，这样两个标签仍在同一侧，而月球那个落在盘面的高侧。位置用 `lunarPlaneLabelRadius: 0.72` + `lunarPlaneLabelLift: 0.26`（沿月球面法线抬起）与 `eclipticPlaneLabelRadius: 1`，径向与竖向都拉开，避让盒测试才不会丢掉其中一个。截图确认：同一侧、一高一低，能直接看出两个面的夹角。

**标签悬停说明**（用户要求，可上网查资料）：
- 外壳侧扩展：`DemoLabelAnchor.descriptionKey?: string`（可选，只有需要解释的标签才给）；`DemoDetailView.vue` 里加 `hoveredLabel` 与一个 tooltip 元素。
- **关键取舍**：tooltip 用**命中测试**实现，而不是让标签自己可悬停。标签层必须保持 `pointer-events: none`，否则鼠标划到文字上就拖动不了相机——为了一个说明文字牺牲相机操作不值。命中测试在 `.demo-stage` 的 `pointermove` 上做，只对带 `descriptionKey` 的标签跑几个矩形判断。
- 12 个标签各配一条说明（中英各 12 条），文案依据 Wikipedia 的 umbra/penumbra/antumbra、solar/lunar eclipse、lunar node、ecliptic、eclipse season 等条目核对（用本地 7890 代理抓取）。
- 新 key 全部经 `ECLIPSE_LOCALE_KEYS` 导出，`registry.test.ts` 会自动校验两个 bundle，因此漏译会直接测试失败。

**验证 tooltip 的办法**：从场景里用 `dispatchEvent(new PointerEvent('pointermove', ...))` 打一个瞄准某标签中心的合成事件，触发外壳**真实的**命中测试，再 `--dump-dom` 读 tooltip 文本并与 locale bundle 逐字比对 ✓。

**顺带修掉**：月食章节首帧显示「没有食」——播放起点正好落在首次接触的边界上，分类会擦边。改成从事件窗口起点往内 1 分钟（`Math.min(60_000, span * 0.01)`）开始，现在日食首帧是「偏食」、月食首帧是「半影月食」。

**悬停说明的第二个坑（拖拽时闪烁）**：`pointermove` 命中测试在**按住按钮拖拽旋转**时会不断触发——鼠标划过每个标签都会弹一次说明，触屏更糟（手指在玻璃上拖动同样上报「按住按钮」）。修法是 `if (event.buttons !== 0) { 清除; return }`，并另外在 `pointerup` 上跑同一个命中测试，这样点一下/轻触标签仍能看到说明并停留。用合成事件验证四种手势：hover → 显示，drag(buttons=1) → **不显示**，tap(pointerup) → 显示，无手势 → 不显示。

**第三个坑（贴边被裁）**：说明框比标签宽且以标签为中心，靠近舞台边缘的标签会有一半文字被裁掉。把 `x` 夹到 `[half + 8, width - half - 8]`，`half` 用与样式表 `min(300px, 74vw)` 一致的口径算（`Math.min(300, window.innerWidth * 0.74) / 2`），两者必须同步改。实测 526px 宽下太阳标签在 x=95，说明框被夹到 158 ✓。

**截图确认了观感**：深色卡片、青色标题、浅灰正文，浮在标签上方，不挡场景主体。

**顺带**：`.gitignore` 补上 `__pycache__/` 与 `*.pyc`（`tools/` 里的 .py 是源码，字节码缓存不是）——问了几次没答复，属于零风险的标准卫生项，直接做了。`git status` 里 `tools/__pycache__/` 已消失。

## 补四：自查 diff 时找到的三处小问题

写完功能后逐行看 diff，又发现三处：

1. **场景重载时说明框不消失**：`mountScene` / `unmountScene` 都清了 `labelEntries`，却没清 `hoveredLabel`，重载后说明框会带着旧标签的文案留在屏幕上。两处都补上 `hoveredLabel.value = null`。

3. **`overlay-hidden-aware` 是死类名**：`src/` 里出现两次、CSS 里零定义。功能面板那处是既有的，我加控制面板时把它复制了一遍。两处一起删掉——不往仓库里添死代码。

**教训**：功能写完不等于收尾完。这三处没有一个能靠测试或截图发现，只有逐行读 diff 才看得见。以后把「读一遍自己的 diff」当成和跑测试同等必要的步骤。

## 补五：把说明做成可访问的

上一轮我指出一个自己造出来的缺口：悬停说明只有鼠标/触屏能用，键盘和读屏用户拿不到。用户回「继续」，就补上了。

**做法**：在控制面板末尾加一个 `<details class="glossary">`（术语说明），列出同样 12 条说明。选 `<details>` 而不是自己写折叠，是因为**键盘行为与展开状态是浏览器白送的**，不用写一行 JS，也不用管 ARIA。默认收起，所以面板只多一行高度，不挤压原有内容。

**顺序**按读者需要排，不按场景发布顺序：天体 → 影的三种 → 平面与交点 → 两个标记。这个顺序在代码里是一条显式的 `GLOSSARY_ORDER` 常量，因为「场景恰好按什么顺序发标签」是实现细节，不该泄漏成阅读顺序。

复用既有 locale 文案，只新增一个 `panel.glossary` 标题键——所以 `registry.test.ts` 自动覆盖，无重复内容。

**验证**：`<details>` 无 `open` 属性（默认收起）✓；summary 为「术语说明（与标签悬停相同）」✓；12 个术语顺序正确 ✓；`<dd>` 共 24 个 = 12 条读数 + 12 条说明 ✓。

## 补六：平面标签位置（用户按截图反馈，来回三轮才找对）

用户要求：黄道面文字放到黄道面**下方**，月球轨道面**靠近**月球轨道。改对了要经过三次错误答案，每次都是被截图否掉的：

1. **错答一：沿「相机 right 向量」放。** 我以为那是画面横向，结果它正好落在**日—地轴**上——因为相机就是沿日—地轴看的。于是两个平面标签挤进太阳/月球/影锥标签堆里，反复被避让挤掉。
2. **错答二：放在椭圆的顶部/底部。** 两个圆盘同心，半径只差 0.7 单位；倾角 5.14° 太小，导致两个椭圆在**顶部/底部只差约 12px**，而在**日—地轴两端差约 29px**（径向未被透视压缩）。所以顶部放的标签说不清属于哪个椭圆。
3. **正解：沿日—地轴，放在「更空的那一端」，并上下错开。** 但「空的一端」不是固定的：**日食时月球在向阳侧，月食时月球在背阳侧**。所以方向要**量出来**——比较两端各自到太阳/月球的距离，取更远的那端。日食取背阳端、月食取向阳端，两边都干净。

**落位**：黄道面在黄道盘**外缘**（1.0r）再叠一个 **+26px 的屏幕位移**（外壳把文字画在锚点上方，所以想让它落到线下方，锚点必须在线下方，且必须用像素——两个章节的 px/单位差约三倍）；月球轨道面在月球盘**内侧**（0.78r）并沿月球面法线抬起 0.16r。这样即使两条边线只差二十来像素，也各自明确。

**顺带调整优先级**：平面标签从最低提到第 2 档（在节点标记之上），因为节点只是个圆点、位置由读数给出，而平面标签是理解倾角的钥匙。

**教训**：这三轮全是「我以为的屏幕方向」和「实际的屏幕方向」不一致。**相机看向哪，决定了哪个方向会被压扁**——放标签前先想清楚相机在哪、哪个方向在屏幕上被透视压缩了。截图是唯一能证伪的判据。
